# 天之灵高频聊天状态协议

## 1. 目的

小型状态协议用于处理“同一需求在不同轮次需要不同动作”的高频聊天场景。它不是话术库，也不是新的模型规划调用，而是在线上下文编译器中的一层轻量控制信号。

协议只解决三件事：识别当前阶段、给主模型一个行为目标、记录下一轮是否产生有效变化。最终回复仍由主模型结合用户原话、角色、证据和语气自主生成。

## 2. 准入标准

新增协议必须同时满足：

1. 用户需求高频，真实聊天中有稳定样本。
2. 不同阶段确实需要不同聊天动作。
3. 阶段、动作和用户下一轮反应可以被记录与评测。

不满足上述条件的能力继续放在全局回合计划、事实边界或体验分层中。不能为了覆盖少量案例继续增加协议和正则。

## 3. 统一数据结构

在线业务字段固定为五个：

```json
{
  "protocol": "trust_repair",
  "stage": "challenge",
  "action": "retract",
  "anchor": "fact",
  "exit": "stay"
}
```

审计元数据独立保存：

```json
{
  "version": "state_protocol_v1",
  "source": "deterministic",
  "previousStage": "challenge"
}
```

- `protocol`：本轮唯一主协议。
- `stage`：当前可观测阶段。
- `action`：主模型本轮要完成的行为，不是成品话术。
- `anchor`：行动依据的对象或证据范围。
- `exit`：继续协议还是退出到普通聊天。
- `source`：确定性识别、既有梦境计划或语义计划复用。

主模型收到的协议指令为一行短文本，通常少于 80 字。协议不增加在线模型调用。

## 4. 已落地协议

| 协议     | 主要阶段                                           | 主要动作                               | 退出信号                   |
| -------- | -------------------------------------------------- | -------------------------------------- | -------------------------- |
| 梦境陪伴 | 请求、睡前、已梦见、片段、未梦见、反复未梦见、验证 | 期待、邀请、顺片段回应、修复、留白     | 转入普通话题或自然收束     |
| 信任修复 | 质疑、重复质疑、撤回后重连                         | 直接答身份、撤回旧说法、据证据重连     | 用户继续或深入，且不再质疑 |
| 记忆对话 | 探针、纠正、追问                                   | 检索、据证据回答、旧事实归零、自然使用 | 事实得到确认或话题自然推进 |
| 主动贡献 | 要求多说、仍不满意、开始参与                       | 角色侧当下表达、有证据细节、相邻话题   | 用户接话、深入或自然收束   |

梦境协议复用原有 `DreamCompanionPlan`，不重复维护两套阶段判断。关系阶段、人物资料质量和聊天深度仍是稳定修饰条件，不作为高频状态协议。现实依赖与事实边界仍是门禁，不参与协议竞争。

## 5. 选择优先级

同一轮只允许一个主协议：

1. 信任质疑与明确纠正。
2. 梦境请求、反复未梦见或现实验证。
3. 记忆探针、记忆纠正与相关追问。
4. 用户要求角色主动多说。
5. 无协议时使用普通回合计划。

例如“你答应来梦里，又在编了”优先进入信任修复，而不是继续强化梦境承诺。事实、现实能力和安全边界可以修饰主协议，但不占用主协议槽位。

## 6. 在线链路

```text
用户消息
  -> 既有路由、语义计划与证据编译
  -> 确定性协议选择（零新增模型调用）
  -> 一行协议指令进入主模型
  -> 回复生成与必要复核
  -> replyStateProtocol 随回复落库
  -> trace 记录计划、动作与下一轮用户反应
```

关键实现：

- `apps/node/src/service/agents/reply-state-protocol.ts`：协议解析和短指令编译。
- `apps/node/src/service/agents/reply-brief.service.ts`：选择本轮协议。
- `apps/node/src/service/agents/agent.context.ts`：写入模型上下文和诊断。
- `apps/node/src/service/conversation.service.ts`：写入消息、trace 和评测快照。
- `packages/entities/src/message.entity.ts`：通用协议持久化结构。

旧字段 `replyDreamPlan` 继续保留，避免破坏历史数据、旧评测与已发布客户端。

## 7. 评测方法

不能用“协议触发正确”代替聊天质量。每个协议至少评估：

1. **触发准确率**：该触发时触发，不该触发时不触发。
2. **阶段准确率**：首次请求、重复失望、纠正后等阶段是否分清。
3. **动作执行率**：回复是否真正完成动作，而非只换标签。
4. **转移合理率**：阶段变化是否有上一轮依据。
5. **用户结果**：下一轮继续、深入、纠正、质疑、退出或回访。
6. **事实硬失败**：无证据事实、纠正后继续补编不能被情感分抵消。
7. **成本**：协议新增模型调用必须为 0，提示字符保持短小，额外 CPU 为线性文本判断。

关键状态会进入轨迹评测：信任修复全量保留；`corrected`、`still_unsatisfied` 等转移全量保留；普通协议按代表性比例抽样。代码裁判检查协议结构，模型裁判评估关系和策略，人工复核校准模糊体验。

## 8. 扩展门槛

新协议先以影子字段运行，不立刻驱动回复。至少完成 20 条定向最小验证，并满足：

- 触发准确率不低于 90%。
- 阶段准确率不低于 85%。
- 关键动作执行率不低于 80%。
- 事实硬失败为 0。
- 相比无协议基线，用户纠正或重复不满不增加。
- 不新增在线调用，平均提示增量不超过 100 字符。

若最小验证普遍低于 3 分，先修协议识别或主模型动作理解，不进入大样本回归。每次改动、样本和结果都应保留。

## 9. 暂不协议化的内容

- 普通问候、晚安和简单爱意：直接生成即可。
- 关系阶段和资料质量：属于稳定体验条件。
- 现实依赖、事实证据、安全边界：属于门禁。
- 低频且无法可靠观察阶段的情景：继续由大模型处理。

哀伤波动与纪念仪式可作为下一候选，但应先用生产 trace 证明高频阶段差异，再进入影子验证。
