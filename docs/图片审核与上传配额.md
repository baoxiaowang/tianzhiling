# 图片内容审核与上传配额

本文是图片审核（数据万象 CI）与上传配额的唯一长期交接文档。修改上传入口、审核范围、审核策略或配额上限前先读本文，修改后同步更新本文。

## 一、背景：2026 年 9 月审核费用结论

账单事实：数据万象「图片内容审核（tianzhiling bucket）」263,002 次、394.50 元。

由此确认的三条口径（依据 [内容审核费用](https://cloud.tencent.cn/document/product/460/58119)、[设置图片审核](https://cloud.tencent.cn/document/product/460/46493)）：

1. 394.50 ÷ 263.002 千次 = **1.5005 元/千次**，正好是「自动审核 / API 调用」单价。存量批量任务走的是「图片内容审核-**闲时**」（0.45 元/千次）且账单行项目名不同，因此**不存在存量扫描任务**。
2. **每个审核场景单独计费**：勾选涉黄、广告、违法违规 3 个场景时，1 张图计 3 次。实际图片数 = 263,002 ÷ 场景数。
3. 原审核配置是**整个存储桶**范围，桶里除帖子图外还有聊天图片、聊天导入截图、头像、封面、用户上传的亲人照片、AI 生成照片和运营资产，全部按上传逐张计费。

因此真正的问题不是"存量扫描"，而是**范围过大 + 场景倍数**。代码侧改造解决"范围"，控制台侧改造解决"场景"。

## 二、代码改动

| 文件 | 作用 |
| --- | --- |
| `apps/node/src/common/upload-policy.ts` | 纯函数判定：哪些目录、哪些后缀属于要审的图片 |
| `apps/node/src/service/image-moderation.service.ts` | 审核策略：分层（公开全量 / 私密红线抽样）、调用审核、解析结果、按配置给出 pass/block |
| `apps/node/src/service/upload-quota.service.ts` | 按用户、按北京自然日的上传配额（Redis） |
| `apps/node/src/service/tencent-cos.service.ts` | 新增 `auditImageByObjectKey`：`GET ?ci-process=sensitive-content-recognition` 传输与 JSON 解析 |
| `apps/node/src/controller/storage.controller.ts` | 上传入口接线：先占配额、再上传、最后审核；违规即删除对象并拒绝返回地址 |
| `apps/node/src/config/config.default.ts` | 新增独立的 `imageModeration`、`uploadQuota` 配置段 |

设计边界：

- 只覆盖腾讯云 COS（生产 `NODE_TENCENT_COS_ENABLED=true`）；`NODE_OSS_ENABLED=false` 的 OSS 直传通道不在本次范围。
- 审核对象是**已上传到桶里的对象**（按 ObjectKey 审核），判定违规后立即 `deleteObject`，客户端拿不到可访问地址。合规上不留违规副本，代价是对象会短暂存在。
- 服务端生成内容（`memorial-photos`，AI 合成照）与运营资产（`admin/*`）**不走该入口**，因此默认不产生审核费用。

## 三、配置项

审核（`imageModeration`）：

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `NODE_IMAGE_MODERATION_ENABLED` | `false` | 关闭时完全保持历史上传行为 |
| `NODE_IMAGE_MODERATION_BIZ_TYPE` | 空 | 审核策略唯一标识；**留空即用默认策略，场景数不受代码控制** |
| `NODE_IMAGE_MODERATION_FOLDERS` | `moments,avatars,contact-covers,conversation-images,chat-imports,memorial-source-photos` | 只在用户产生内容的目录审核 |
| `NODE_IMAGE_MODERATION_RESTRICTED_FOLDERS` | `conversation-images,chat-imports,memorial-source-photos` | 私密目录：改用红线策略 + 抽样 |
| `NODE_IMAGE_MODERATION_RESTRICTED_BIZ_TYPE` | 空 | 私密目录的红线策略；留空退回 `BIZ_TYPE`（仍会审，只是不省钱） |
| `NODE_IMAGE_MODERATION_RESTRICTED_SAMPLE_RATE` | `0.05` | 私密目录抽样比例，5% |
| `NODE_IMAGE_MODERATION_FOLDER_SAMPLE_RATES` | `{"memorial-source-photos":1}` | 按目录覆盖抽样比例，优先于上面一项 |
| `NODE_IMAGE_MODERATION_REVIEW_ACTION` | `allow` | 疑似（Result=2）：`block` 拦截，其他值放行并记日志 |
| `NODE_IMAGE_MODERATION_FAILURE_ACTION` | `allow` | 审核不可用：`block` 拦截，其他值放行并告警 |
| `NODE_IMAGE_MODERATION_LARGE_IMAGE_DETECT` | `false` | 开启后 >5MB 图片压缩后审核，产生基础图片处理费用 |
| `NODE_IMAGE_MODERATION_TIMEOUT_MS` | `8000` | 单次审核超时 |
| `NODE_IMAGE_MODERATION_LOG_RAW` | `true` | 打印审核原始响应；首次上线核对返回结构后应关闭 |

配额（`uploadQuota`，按北京时间自然日、按用户计数）：

| 环境变量 | 默认值 | 说明 |
| --- | --- | --- |
| `NODE_UPLOAD_QUOTA_ENABLED` | `true` | 关闭后不做任何配额限制 |
| `NODE_UPLOAD_QUOTA_DAILY_FILES` | `50` | 单用户每日文件总数 |
| `NODE_UPLOAD_QUOTA_DAILY_IMAGE_FILES` | `30` | 单用户每日图片数（约平台全站真实日均的 15 倍） |
| `NODE_UPLOAD_QUOTA_DAILY_BYTES` | `268435456`（256MB） | 单用户每日总字节；客户端上传前不压图，一次导入 30 张截图最坏约 150MB，故留 256MB |
| `NODE_UPLOAD_QUOTA_FOLDER_LIMITS` | `{"chat-imports":30,"moments":27,"conversation-images":15,"avatars":5,"contact-covers":5,"memorial-source-photos":10}` | 目录级上限，JSON。`moments` 按 3 帖 × 9 图；亲人照片与纪念馆每日生成配额（非会员 3 / 会员 10）对齐 |
| `NODE_UPLOAD_QUOTA_EXEMPT_FOLDERS` | `chat-imports` | 豁免"文件数/图片数"全局计数的目录（一次性批量流程）；**仍计入全局总字节**，且必须自己配了目录上限才生效（漏配即退回普通目录） |

限额设为 `0` 或负数表示**不限制该维度**。配置为非法 JSON 时回退默认值，不会阻塞启动（有测试覆盖）。

聊天导入为什么要豁免：客户端单批最多 30 张截图、长聊天记录可能上百张，若与日常额度共用，30 张的日常上限会被一次导入吃光，用户当天连一张聊天图片都发不出去。豁免后它的预算是独立的 `chat-imports: 30`（一天一批），代价是长聊天记录需要分多天导入。

### 分层审核：公开全量 / 私密红线抽样

判断"某个上传流程要不要逐张实时审"的判据不是私密与否，而是三条：**是否公开可传播**、**是否进入大模型**（进入即受生成式 AI 服务合规约束）、**发现后能否处置**。据此分三层：

| 层 | 目录 | 默认策略 | 抽样 |
| --- | --- | --- | --- |
| 公开可传播 | `moments`、`avatars`、`contact-covers` | `NODE_IMAGE_MODERATION_BIZ_TYPE`（全场景） | 全量 |
| 私密但进模型 | `conversation-images`、`chat-imports` | `NODE_IMAGE_MODERATION_RESTRICTED_BIZ_TYPE`（只勾色情等红线） | 5% |
| 私密且进生成链路 | `memorial-source-photos` | 同上（红线策略） | **全量**（`folderSampleRates` 覆盖为 1） |

关键取舍：

- **亲人素材保持全量**：它进入 AI 合成链路，是深度合成合规的重点，不能靠抽样。
- **抽样用对象键确定性哈希**，同一张图结论稳定、可复现，便于按日志核对覆盖率；对象键本身含随机片段，整体均匀。
- **漏配红线策略时私密目录退回默认策略**（宁可多审不漏审）；**未传目录时不判为私密**。
- **配置写错不会静默降级**：`FOLDER_SAMPLE_RATES` 里若全是非法值，整体回退默认值而不是变成空表；显式 `{}` 才表示清空覆盖。
- 场景侧的红线是**色情内容**（含涉未成年，刑事红线）；**广告内容、低质内容与平台合规无关，必须去掉**（低质内容还会额外产生图片质量检测费）。

抽样比例只影响成本，不影响"发现即处置"义务——抽样之外仍依赖举报入口与人工巡检，见"已知风险"。

## 四、行为矩阵

| 审核返回 | 默认动作 | 客户端可见错误 |
| --- | --- | --- |
| `Result=0` 正常 | 放行 | — |
| `Result=1` 违规 | 删除对象 + 拒绝 | `IMAGE_MODERATION_BLOCKED`（400，图片内容未通过安全审核） |
| `Result=2` 疑似 + `reviewAction=block` | 删除对象 + 拒绝 | `IMAGE_MODERATION_REVIEW_REQUIRED`（400，需人工复核） |
| `Result=2` 疑似 + `reviewAction=allow` | 放行 + warn 日志 | — |
| 私密目录未抽中（抽样外） | 放行 + info 日志 | — |
| 超时/报错/结构无法识别 + `failureAction=block` | 删除对象 + 拒绝 | `IMAGE_MODERATION_UNAVAILABLE`（503） |
| 超时/报错/结构无法识别 + `failureAction=allow` | 放行 + error 日志 | — |
| 配额超限 | 拒绝，**不上传** | `UPLOAD_DAILY_LIMIT_EXCEEDED`（429，含 reason/limit/used） |
| 图片走 `/storage/cos/sign-upload` | 拒绝，要求改走 `/storage/upload` | `IMAGE_UPLOAD_REQUIRES_SERVER_RELAY`（400） |

提示：被审核拦截的图片**照常占用配额**（防止用拒绝结果免费刷配额），上传失败（COS 报错）才会回补配额。豁免目录（聊天导入）只计自己的目录上限与全局总字节，不消耗全局文件数/图片数。

## 五、控制台配套改动（必须做，否则省不下钱）

代码只解决"审哪些"，**场景倍数和桶级重复审核必须在控制台处理**。

1. 数据万象控制台 → 存储桶管理 → `tianzhiling-1336785558` → 内容审核 → **审核策略**：建**两个**图片审核策略——公开策略（全场景，建议含色情 + 其他违规）和红线策略（**只勾色情内容**，去掉广告内容与低质内容）。两个 BizType 分别填到 `NODE_IMAGE_MODERATION_BIZ_TYPE` 与 `NODE_IMAGE_MODERATION_RESTRICTED_BIZ_TYPE`。去掉广告即省 1/3，去掉低质内容还省掉额外的图片质量检测费。
2. 内容审核 → **自动审核配置 → 图片审核**：**删除"整个存储桶"那条规则**（否则同一张图既被桶级规则审、又被代码审，费用翻倍）。若仍想保留桶级兜底，改用前缀匹配且与代码范围一致。
3. 需要历史存量合规时，用 **历史数据审核任务**（0.45 元/千次，闲时价），不要用自动审核全量刷。
4. 控制台限制"多条配置路径不能重复或存在包含关系"：删掉整桶规则后才能加前缀规则；前缀是对象键前缀，正确写法是 `moments/`，**不是** `static/moments/`（对象键为 `目录/年/月/日/文件名`，传了 `folder` 就不再拼 `static`）。

## 六、上线顺序（不要颠倒）

1. 控制台先建好审核策略，确认场景数与 BizType。
2. 配置 `NODE_IMAGE_MODERATION_ENABLED=true`、`BIZ_TYPE`、`LOG_RAW=true` 并发布。
3. 观察 `[image-moderation] audit response` 日志，**核对真实返回结构与 `parseImageAuditResponse` 的假设一致**（重点看是否有 `RecognitionResult.Result` 与各场景 `HitFlag`）。确认无误后把 `LOG_RAW` 关掉。
4. 确认代码审核稳定后，再删除桶级整桶自动审核规则。
5. 观察 1-2 天：`[image-moderation] passed/blocked` 比例、`UPLOAD_DAILY_LIMIT_EXCEEDED` 次数、以及内容审核 → 审核详情里的审核量是否降到"UGC 图片数 × 保留场景数"。

若第 4 步先做、第 2 步未生效，会出现**审核真空**，禁止颠倒。

## 七、验证与观测

- 审核决策：`grep '\[image-moderation\]' <node 日志>`，包含 decision、reason、folder、userId、label、score。
- 拦截：`[storage] upload rejected by image moderation`，以及删除失败时的 `failed to delete rejected object`（出现即说明桶里残留违规对象，需人工删除）。
- 配额：`[upload-quota]` 前缀的 warn 日志（Redis 故障放行、跨天不回补）；业务侧看 429 错误码分布。
- 费用核对：控制台「审核详情」支持按审核方式筛选（API 调用 / 自动审核 / 历史数据审核）并导出 xlsx，按 `resourcePath` 前缀分组即可核对。

## 八、回滚

- 审核：`NODE_IMAGE_MODERATION_ENABLED=false` 并重启，立即恢复历史行为（上传成功即返回）。
- 配额：`NODE_UPLOAD_QUOTA_ENABLED=false` 并重启。
- 两者都不改动数据结构，不需要回滚迁移。已删除的违规对象不可恢复，属预期。

## 九、已知风险与未覆盖

1. **疑似放行是默认策略**：没有人工复核队列，`Result=2` 只记日志。需要更严时设 `REVIEW_ACTION=block`，代价是误伤正常图片、客服量上升。
2. **审核不可用默认放行**：保证可用性优先。合规要求更严时设 `FAILURE_ACTION=block`。
3. **AI 产物不审是产品决策**：`memorial-photos` 由模型生成、不经用户上传通道，默认不审。若合规要求覆盖 AI 产物，需要在生成链路单独接审核，不能只靠上传入口。
4. **配额按用户计数，未覆盖未登录/异常请求**：`/storage/upload` 由鉴权中间件保护，缺少用户标识时跳过配额并告警，审核仍然生效。
5. **聊天导入一天一批**：`chat-imports: 30` 与客户端单批上限相同，长聊天记录需分多天导入。若客服反馈集中，先调 `NODE_UPLOAD_QUOTA_FOLDER_LIMITS` 里的 `chat-imports`，不要动全局图片上限。
6. **审核结果未回调到 App**：目前只有 console 冻结与代码删除两种处置；后续若要做人工复核队列，应新增审核回调接收端，而不是扩大自动审核范围。
7. **私密目录只抽样 5%**：抽样之外没有实时发现能力，必须靠举报入口与人工巡检补足；这是抽样方案的前提，未建立处置链路前不要把比例调得更低。
8. **分层依赖控制台建了两个策略**：`RESTRICTED_BIZ_TYPE` 留空时私密目录会退回公开策略（仍会审，但不省钱），代码不会报错，需要靠「审核详情」里的场景数核对。
