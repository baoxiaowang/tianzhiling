# T5：旧事来源计数器（5 个审计字段）

> 每轮记录旧事通过哪条路径进入了上下文，为后续按路径修复提供数据。

## 问题

旧记忆乱入有五条已知路径（A-E），但没有按路径的注入计数。修了 E 后只能看总失败率，无法知道 A-D 谁还在贡献。

## 方案

在助手消息上增加 5 个可选布尔字段（全无索引，纯增量）：

```ts
// 旧事来源路径计数器（T5）
legacyRetrievalInjected?: boolean;   // 本轮是否通过 legacy 检索注入了旧事
invitationTriggered?: boolean;      // 请柬是否触发（复用已有 replyMemoryRetrievalInvitation 的非空判断）
historyOldFactPresent?: boolean;    // 历史消息窗口内是否有未被本轮 cue 的旧事
summaryOldFactPresent?: boolean;    // continuity summary 中是否包含旧事
profileFactInjected?: boolean;      // 画像事实是否注入了 episodic 类（cue-gated 类）
```

### 实现位置

在 `apps/node/src/service/conversation.service.ts` 的消息持久化路径（`createAssistantReplyMessages` 或 `saveMessage`）：

```text
legacyRetrievalInjected：从 routing.memoryRetrievalMode === 'active' 且有检索结果推导
invitationTriggered：从 routing.memoryRetrievalInvitation 非空推导（复用已有字段逻辑）
historyOldFactPresent：从上下文构建时的历史消息扫描推导
summaryOldFactPresent：从 continuitySummary 是否包含旧事内容推导
profileFactInjected：从画像事实注入的 gate 结果推导
```

### 判定逻辑

```text
"旧事"的定义：用户在过去轮次提到但现在未主动提起的具体事实
简化判定（够用即可，不做完美 NER）：
  - 检索结果中包含非本轮产生的 retrieved_user 类型证据 → legacyRetrievalInjected = true
  - 历史消息中包含 >24h 前的用户消息且未被当前段 cue → historyOldFactPresent = true
  - summary 包含"以前/曾经/上次"等旧事表述 → summaryOldFactPresent = true
  - 画像 episodic 类事实被注入 → profileFactInjected = true
```

## 验收

1. 5 个字段落库（本地测试数据库）
2. 可以按路径统计旧事注入量（聚合查询）
3. 不改变任何回复行为（纯观测）

## 边界

- 只加观测，不加控制
- 不新增索引
- 判定从简——计数器的目的是区分"哪条路径在贡献"，不是精确判定每次注入是否合理
- 字段全可选，micro/短路径可为空
