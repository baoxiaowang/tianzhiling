# 记忆模块接口草案（v0）

状态：**只定口子和字段，不写实现**。这份草案决定"边界画在哪"，实现和切换排在后面。

## 0. 这份草案解决什么

把"对话记忆"（用户说过的原话、由原话聚成的一件件事、还没了结的事）做成一个可替换的模块，
让上层对话流程只认一个门面，底下换引擎不用动业务代码。

**不解决**：亲人称呼、去世时间这类必须一字不差的精确参数。它们是产品契约，永远独立于记忆引擎。

## 1. 分工原则（四层，谁也不能越界）

| 层     | 负责                                                                      | 不负责                       |
| ------ | ------------------------------------------------------------------------- | ---------------------------- |
| 事实源 | 用户和 AI 的原话消息（数据库里那份，唯一副本）                            | 任何提炼                     |
| 引擎   | 从原话建索引、组合、清单；按查询把证据找出来                              | 决定要不要注入、用什么口径说 |
| 策略层 | 进门过滤（事实型/非情绪/非问句）、出门过滤（含检索键/人物对齐）、注入条数 | 存储、检索算法               |
| 契约层 | 精确参数、身份与关系设定、安全红线                                        | 随引擎变化                   |

引擎的所有产物都是**派生物**：可以删掉、可以从原话重建。这是"随时能切回来"的前提。

## 2. 门面与五个口子

```ts
/** 上层唯一入口。切换引擎只换这个接口背后的实现。 */
export interface MemoryModule {
  /** 口子 5：这套引擎支持什么。上层据此决定怎么用它。 */
  capabilities(): MemoryCapabilities;

  /** 口子 1：写入。一轮对话结束后把原话交给引擎。 */
  ingest(request: MemoryIngestRequest): Promise<MemoryIngestResult>;

  /** 口子 2：检索。这一轮该带出哪些证据。 */
  recall(request: MemoryRecallRequest): Promise<MemoryRecallResult>;

  /** 口子 3：清单。读还没了结的事。 */
  listOpenItems(
    request: MemoryOpenItemsRequest
  ): Promise<MemoryOpenItemsResult>;

  /** 口子 3：清单记账。用户说了结果、或明确不想提，更新状态。 */
  updateOpenItem(
    request: MemoryUpdateOpenItemRequest
  ): Promise<MemoryUpdateOpenItemResult>;

  /** 口子 4：维护。重建 / 遗忘 / 诊断，只给运维和评测用。 */
  maintain(request: MemoryMaintenanceRequest): Promise<MemoryMaintenanceResult>;
}
```

五个口子之外不再开口。**接口越窄，越容易换引擎。**

## 3. 字段定义

### 3.1 公共输入片段

```ts
/** 参与记忆的一轮消息。原话就是这里的 content，引擎不得改写。 */
export interface MemoryTurnMessage {
  messageId: string;
  role: "user" | "assistant";
  content: string;
  occurredAt: string; // ISO，消息真实发生时间
  type?: "text" | "voice" | "image";
}

/** 检索时已经在上下文里的最近消息，用于去重和判断"上次说到哪"。 */
export interface MemoryRecentTurn {
  messageId: string;
  role: "user" | "assistant";
  content: string;
  occurredAt: string;
}
```

### 3.2 口子 1：写入

```ts
export interface MemoryIngestRequest {
  userId: string;
  conversationId: string;
  agentId: string; // 用户在跟哪位亲人说话
  turnMessages: MemoryTurnMessage[];
  /** 上一轮同会话消息，给引擎做归并判断（这句是不是同一件事的后续）。 */
  previousTurnMessages?: MemoryTurnMessage[];
  now?: string;
}

export interface MemoryIngestResult {
  status: "accepted" | "skipped" | "deferred" | "failed";
  /** 异步管线的任务 id，便于诊断与重放。 */
  taskIds?: string[];
  /** 跳过/失败的原因，必须可读，便于运维排查。 */
  reason?: string;
  /** 这次写入归属于哪些事件组合（引擎支持组合时给出）。 */
  groupIds?: string[];
}
```

写入必须**幂等**：同一条 messageId 重复提交，结果一致，不产生重复组合或重复成员。

### 3.3 口子 2：检索

```ts
export interface MemoryRecallRequest {
  userId: string;
  conversationId: string;
  agentId: string;
  /** 用户这一轮的原话（未经拼接），过滤与人物对齐都基于它。 */
  currentUserText: string;
  /** 当前这轮的消息 id，必须排除，不能把用户刚说的话当记忆带回来。 */
  currentTurnMessageIds: string[];
  /** 这一轮在说谁（上层人物对齐的结果）。引擎可据此缩小范围，但不得据此编造。 */
  focusPersonRef?: string;
  recentMessages: MemoryRecentTurn[];
  limit: number; // 期望返回的条数上限
  now?: string;
}

/** 一条可用的证据。 */
export interface MemoryEvidence {
  id: string;
  /** utterance=原话；group_member=组合里的原话；group_summary=组合摘要（只能当背景）；fact=结构化事实。 */
  kind: "utterance" | "group_member" | "group_summary" | "fact";
  text: string;
  role?: "user" | "assistant";
  occurredAt?: string;
  /** 回溯：这条证据来自哪几条原话。group_summary 也必须给，否则不可用。 */
  sourceMessageIds: string[];
  /** 所属事件组合（一件事）。引擎不支持组合时为 undefined。 */
  groupId?: string;
  groupTitle?: string;
  /** 这条证据说的是谁，用于人物对齐。 */
  personRef?: string;
  /** 事实强度：只追加不可覆盖的事实给 effectiveFrom/effectiveTo。 */
  effectiveFrom?: string;
  effectiveTo?: string;
  score?: number;
  /** quote=可以按原话引用；context=只能当背景，不得当作用户说过的事实断言。 */
  assertPolicy: "quote" | "context";
  /** 哪套引擎产生的，切换与对照要用。 */
  engine: string;
}

export interface MemoryRecallResult {
  evidence: MemoryEvidence[];
  status: "ok" | "empty" | "skipped" | "failed";
  diagnostics: {
    engine: string;
    mode: MemorySwitchMode;
    candidateCount: number;
    selectedCount: number;
    groupCount?: number;
    skipReason?: string;
    errorCode?: string;
    elapsedMs?: number;
  };
}
```

**检索口子的三条硬约束**：

1. 只返回 `role: 'user'` 的原话（AI 说过的话不能当用户记忆）；
2. 每条证据必须能回到原话（`sourceMessageIds` 不可为空）；
3. 引擎只负责"找出来"，过滤与人物对齐由策略层统一做，两套引擎用同一套规则。

### 3.4 口子 3：未了结清单

```ts
/** 状态变更只追加，永不覆盖：任何一次状态变化都能回答"谁改的、依据哪句话、什么时候"。 */
export interface MemoryOpenItemStateEvent {
  state: MemoryOpenItem["state"];
  changedAt: string;
  /** 触发这次变化的原话；由用户明确要求置为 dismissed 时也必须有。 */
  evidenceMessageId?: string;
  source: "offline_extraction" | "online_raise" | "user_request";
}

export interface MemoryOpenItem {
  id: string;
  /** 挂在哪个事件组合上（引擎支持组合时给出）。 */
  groupId?: string;
  /** 一句话说清这件没完的事，必须来自原话。 */
  summary: string;
  subjectRef?: string; // 谁的事
  /** 当前状态。只有两方能改，见 §8.2：离线抽取任务改判定；用户明确要求时可置 dismissed。 */
  state:
    | "reported"
    | "awaiting_result"
    | "action_committed"
    | "resolved"
    | "dismissed"
    | "expired";
  /** 状态变更历史，只追加。 */
  stateHistory: MemoryOpenItemStateEvent[];
  importance: 1 | 2 | 3;
  dueAt?: string; // 大约什么时候该有结果
  lastRaisedAt?: string; // 上次提起是什么时候（避免查岗感）。回复链路的记账字段。
  raisedCount: number;
  sourceMessageIds: string[];
  updatedAt: string;
}

export interface MemoryOpenItemsRequest {
  userId: string;
  conversationId: string;
  agentId: string;
  now?: string;
}

export interface MemoryOpenItemsResult {
  items: MemoryOpenItem[];
  status: "ok" | "empty" | "failed";
  diagnostics: { engine: string; total: number; errorCode?: string };
}

export interface MemoryUpdateOpenItemRequest {
  userId: string;
  itemId: string;
  /** 状态判定由离线抽取任务写入（见 §9）。回复链路不判定状态。 */
  state?: MemoryOpenItem["state"];
  /** 只追加：新的说法连同原话一起记，不覆盖历史。 */
  note?: string;
  evidenceMessageId?: string;
  /** 这一轮提起了。这是"记账"不是"判定"，由回复链路在提出后写入。 */
  raised?: boolean;
  now?: string;
}

export interface MemoryUpdateOpenItemResult {
  status: "updated" | "not_found" | "failed";
  item?: MemoryOpenItem;
}
```

清单**只记账、不决定说不说**：什么时候提、提哪件、要不要跳过，由模型结合当轮情况判断。

### 3.5 口子 4：维护

```ts
export type MemoryMaintenanceAction =
  | {
      action: "rebuild";
      scope: "user" | "all";
      userId?: string;
      fromMessageAt?: string;
    }
  | {
      action: "regroup";
      userId: string;
      groupIds?: string[];
      fromMessageAt?: string;
    }
  | {
      action: "forget";
      userId: string;
      evidenceIds?: string[];
      groupIds?: string[];
      messageIds?: string[];
    }
  | { action: "inspect"; userId: string; conversationId?: string };

export interface MemoryMaintenanceResult {
  status: "ok" | "accepted" | "failed";
  affected?: number;
  detail?: Record<string, unknown>;
}
```

`rebuild` 必须幂等且可重放：同一批原话重建两次，结果必须一致。
`regroup` 是组合的纠错入口：聚错了可以按时间窗重算，不需要删数据。

`forget` 只留给运维纠错：用户端删不了派生记忆，他们只能删自己的一条原话，那种删除走
"原话删除事件 → 重算"的路径（见 §6 第 4 条）。运维用 `forget` / `regroup` 纠正错误分组时，
纠正结果必须能持久化，让 `rebuild` 尊重它，而不是把错误分组重新算出来。

## 4. 切换与灰度

```ts
export type MemorySwitchMode = "off" | "shadow" | "active";

export interface MemorySwitchConfig {
  mode: MemorySwitchMode;
  /** 生效引擎。 */
  primary: string;
  /** 影子引擎：只在 shadow 模式下跑，结果只记录、不注入。 */
  shadow?: string;
  /** 生效范围：全局 / 用户名单 / 用户＋角色。 */
  scope: {
    userIds?: string[];
    cohortSha256?: string; // 冻结名单，沿用现有做法
    perAgent?: boolean;
  };
  /** 策略层参数（两套引擎共用）：注入上限、最小实义字数等。 */
  policy: {
    injectLimit: number;
    minEvidenceCharacters: number;
    requireRetrievalKey: boolean;
    personAlignment: boolean;
    dropEmotional: boolean;
    dropQuestion: boolean;
  };
}
```

切换规则：

- **off**：只走精确参数，不调用记忆引擎；
- **shadow**：`primary` 与 `shadow` 都跑，**只有 primary 的结果进上下文**，shadow 的结果进对照记录；
- **active**：只跑 primary。

数据隔离：每个引擎的派生产物带自己的 engine 标记（向量集合名、组合表字段）。切引擎 = 新引擎按原话重建 + 改 `primary`，不做数据迁移、不共用同一份索引。

## 5. 错误与降级契约

- 引擎失败**不能**让回复失败：`recall` 失败返回 `status: 'failed'` + 空证据 + errorCode，上层照常回复；
- 写入失败可重试，必须有任务 id 和可读原因；
- 每个口子受 `limits.recallBudgetMs` 约束，超时即降级为"这轮没有记忆"；
- 影子引擎的任何异常只记录，不影响 primary。

## 6. 硬性约束（写进接口，不靠自觉）

1. **原话不可变**：引擎不得改写、不得删除事实源里的消息；
2. **事实只追加**：新说法追加新版本并写 `effectiveFrom`，旧版本标 `effectiveTo`，永不覆盖；
3. **组合摘要只能当背景**（`assertPolicy: 'context'`），任何可断言的内容必须回原话；
4. **删除要级联（已定）**：用户端只有一种删除——**删自己的一条原话**（删不了 AI 的消息，
   也删不了一条"派生记忆"）。所以级联只有一种形状：删原话 → 重算由它派生的东西。
   组合还有别的成员就重算摘要，成员删空就整组删除；清单条目还有别的证据就重算，证据全没了就删除；
   索引行一并清掉。删除动作留痕（谁删的、什么时候、删了什么），不留内容。
   原话没了就是终态，重建不会把它变回来——**不需要抑制记录**。
   派生物的删除只留给运维纠错（见 `regroup`）：纠正过的分组要能持久化，让重建尊重纠正结果。
5. **可审计**：任意一条证据都能回答"来自哪句话、什么时候说的、由哪套引擎产生"。

## 7. 明确不做

- 不做精确参数（称呼、去世时间）的存储与切换；
- 不做注入过滤策略（它属于策略层，两套引擎共用）；
- 不在本模块里决定"要不要主动关心"（那是模型结合清单的判断）；
- 不做插件市场：只维护"一个窄接口 + 两套实现"。

## 8. 已定决策

### 8.1 组合由引擎自己聚

引擎自己决定"这几句话是同一件事"。由此产生的必然后果：

1. **接口要开组合的纠错口**：`regroup`（见 3.5），聚错能按时间窗重算；
2. **分组必须确定性**：同一批原话重建两次必须得到同样的分组（固定候选顺序、固定判定标准、无随机），否则影子对照评测没有意义；
3. **宁可少聚，不可错聚**：拿不准就不并成一件。错聚会把"完整情况"变成"错误情况"，比碎片严重；
4. **分组判定标准（写死）**：同一个主体 + 同一类事 + 生命周期连续，算同一件事。戒烟"没抽 → 又抽了 → 你以前劝我"是同一件；"这次复查"有了结果之后、下次复查重新提起，算新的一件，但新组合要关联旧组合（保留历史）；
5. **组合要有标题和状态**：标题由引擎写（只当背景，不可断言）；状态由离线任务写（见 8.2）。

### 8.2 清单状态由离线抽取任务判定（已确认）

回复链路**不判定状态**，只读取清单；状态迁移由离线抽取任务在消息落库后判定并写回。
"提问记账在线、状态判定离线"这个拆法**已确认**。

| 事项                                                                    | 谁写                   | 为什么                                                         |
| ----------------------------------------------------------------------- | ---------------------- | -------------------------------------------------------------- |
| **提问记账**：这一轮提起了（`raised` / `lastRaisedAt` / `raisedCount`） | 回复链路，提出后立即写 | 是"发生了什么"的事实，不写会导致重复追问、查岗感               |
| **状态判定**：有了结果 / 已了结 / 用户不想提（`state`）                 | 离线抽取任务           | 是"用户说了什么"的理解，需要看用户原话，且要防模型替用户下结论 |

**在线记账的四条要求**：

1. 不阻塞回复：写完是附带动作，失败只记录、不改变这一轮的回复；
2. 按轮幂等：同一轮同一件事只记一次，重试不会把 `raisedCount` 加两次；
3. 只记事实：只写"提出了"，不写"用户什么反应"；
4. 必须带 `evidenceMessageId`：能回指到是哪一轮提出的。

**离线任务的四条要求**：

1. 判定输入是两头的原话——AI 提起时问了什么 + 用户之后答了什么；
2. 只看用户原话：AI 的问句不能作为了结依据（防"自己问自己答"）；
3. 不确定就不动：含糊的回答保持"还没结果"，宁可留着也不能替用户宣布了结；
4. 幂等且可审计：已了结的不重复写，每次状态变化进 `stateHistory`（谁改的、依据哪句话、什么时候）。

**由此带来的延迟是可接受的**：用户当轮说"结果没事了"时，清单可能还没更新。这不影响当轮回复——用户自己的话本来就在上下文里；清单更新的价值在之后的轮次。离线任务积压只会让"该了结的没及时了结"，不会造成骚扰——因为防重复追问靠的是在线的 `lastRaisedAt`。

## 9. 其余决策（本人已定，不再等确认）

3. **人物焦点由上层算好传入**：亲属称谓归组、已知人物本来就在上层，引擎重复推导只会和上层不一致。引擎可据此缩小范围，但不得自己认定人物关系。上层没传时，引擎不做人物过滤。
4. **影子记录只存诊断、不存正文**：存候选条数、分数、命中/被过滤的证据 id 列表和引擎版本；需要看内容时按 id 回原话取（有权限的评测脚本读）。保留期 14 天滚动删除，避免线上长期堆积原文副本。
5. **回归基线固定五条**：精确参数与身份设定不受影响；记忆失败不影响回复；注入上限与过滤规则不变；同一批原话不重复索引、不重复注入；现有评测结果不下降。这五条做成回归用例。
6. **删除级联（已定）**：用户端只能删自己的一条原话——删了就重算派生品（组合摘要、清单、索引），原话没了就是终态，不需要抑制记录。派生物的删除只用于运维纠错，纠正结果要能被重建尊重。

## 10. 新引擎最小实现范围（v1，本人已定）

目标：在**不改动线上现有行为**的前提下，验证"事件组合 + 未了结清单"能不能改善
"用户隔几天回来、只叫一声"这种场景的体验。

### 做

1. **事件组合最小闭环**：写入时只对"事实型原话"（沿用现有进门过滤）聚成组合；
   组合只有：标题（只能当背景）、成员原话 id、时间跨度、主体、engine 标记。
2. **组合级检索**：命中组合 → 返回成员原话（有条数和长度上限），
   仍然走现有策略层的全部过滤（检索键、人物对齐、情绪与问句剔除）。
3. **未了结清单最小版**：离线抽取任务负责建条目与判定状态；在线只写"这一轮提起了"；
   清单以**参考材料**形式常驻上下文，不替模型挑一件。
4. **影子模式**：新引擎只写诊断、不注入；按用户名单与旧引擎跑同一批消息做对照。
5. **维护**：`rebuild`（按用户/时间窗）、`regroup`（纠错并持久化纠正结果）、`inspect`。

### 不做（v1 明确不做）

- 不做完整的双时间戳与生效区间（先把时间打在成员和组合上，事实版本留到 v2）；
- 不做跨会话的历史关联（"下次复查"关联"上次复查"留到 v2）；
- 不改精确参数、不改注入策略、不改对话流程；
- 不做多引擎同时注入。

### 验收（允许切一小批用户的前提）

1. **对照不劣**：同一批用户、同一批消息，人工抽检新引擎的证据在"相关性、完整性"上不弱于旧引擎；分不清的算旧引擎赢；
2. **回归基线五条全过**；
3. **重建幂等**：同一批原话重建两次，分组一致；
4. **失败降级**：新引擎挂掉，回复不受影响；
5. **成本可控**：写入的模型调用量、影子期双跑的耗时在预算内。

### 观察点

- 分组质量：错聚比碎片严重，v1 只在"同一主体 + 同一类事"的窄场景开启；
- 数据隔离：影子里绝不能出现"新引擎写入影响旧引擎"；
- 清单常驻的副作用：观察模型一轮里会不会提太多件事。

## 11. 实现状态（v1 已落地）

### 已实现

### v1 规则抽取的线上实测结论（2026-09）

用线上 30 天数据回测（活跃 400 人 + 随机 400 人两档）：

| 指标                                | 活跃用户  | 随机用户 |
| ----------------------------------- | --------- | -------- |
| 每人每月宽信号候选（收紧前）        | 36.3 条   | 3.5 条   |
| 收紧后成条（具体事项 + 未完成信号） | 0.7 条    | 0.1 条   |
| 有任一条目的用户                    | 145 / 400 | 27 / 400 |
| 削减比例                            | 98.2%     | 97.4%    |

**结论：确定性的规则抽取在这类聊天里不成立。** 保留下来的人工抽检样本里，
回忆过去时（"那时候""去年"）、情绪思念（"没走""梦里"）、日常作息（"明天上班""准备去上班"）、
别人的一般状态（"他还没结婚"）混在一起，真正的待跟进事项只占少数；
而且收紧后召回几乎归零。规则读不出"这是一件要跟进的事"和"这是一段回忆"的区别。

**因此回归原定方案**：未了结条目的抽取与状态判定改由**离线模型判定**，规则只留两个用途：
① 限定候选窗口；② 事后校验（每条必须能指回输入里的原话、类别在允许集合内、状态迁移沿用只追加规则）。

### 模型判定的线上回测（2026-09）

模型：qwen-plus（DashScope 兼容接口）。窗口：30 天。

| 指标                              | 活跃 20 人 | 随机 25 人（只给事实型） | 随机 25 人（给全部原话） |
| --------------------------------- | ---------- | ------------------------ | ------------------------ |
| 有事件的用户                      | 12 / 20    | 1 / 25                   | 6 / 25                   |
| 每人成条                          | 1.55       | 0.05                     | 0.32                     |
| 程序拒掉（引用对不上/类别不合规） | 10         | 4                        | 4                        |

抽检结论：真正的"过几天该问一句"的事情占多数——
"钱留给儿子看病，明天儿子又要复查了""我挂了明早的号""明天晚上我就坐车去陕西了"
"我明天要去考科目二、科目三了""买了下周二去丽江的机票"都是准的；
仍有少量回忆句（"自从你上一年级我们就分开了"）和情绪句混进来，靠安全过滤挡掉一部分。

两条已固化的结论：

1. **候选窗口**：消息少的用户（≤40 条）直接把全部最近原话交给模型——只给事实型会把召回压掉约 6 倍
   （0.32 → 0.05 条/人）；消息多的用户先按事实型收窄，再截最近 60 条。
2. **模型选择**：默认的对话模型（doubao-seed-character）做这件事明显不听话（话题乱标、捞出"你走了以后"这类情绪句）；
   这个任务应当单独配一个"听话的指令模型"，用 `NODE_MEMORY_OPEN_ITEM_BASE_URL / API_KEY / MODEL` 三个变量指定，
   不配时回落到默认模型。

## 12. 离线排期怎么挂（v1 已接上）

未了结清单的抽取复用现有记忆管线的"任务表 + 队列 + 协调任务"，不新建调度器：

1. **一种新任务**：`open_item_extraction`（每用户每天一条）。
   - 任务的 `messageId` 用**用户 id**当合成键，配合现有 `(messageId, kind, pipelineVersion)` 唯一索引天然去重；
   - 日期（北京时间 YYYY-MM-DD）进 `pipelineVersion`，所以一天一条，跨天自动是新的一条。
2. **合并窗口**：用户每来一条消息就把这条任务的 `nextAttemptAt` 顺延到"当前时间 + 30 分钟"，
   同一段聊天只跑一次；当天已跑过时最多再重开两次（每人每天最多 3 次模型调用）。
3. **谁来执行**：不直接往队列里塞 job，交给**每 5 分钟一次的协调任务**按 `nextAttemptAt` 拾取，
   由记忆 worker（现在是 3 并发）执行；worker 挂了、任务失败都有现成的重试与积压机制。
4. **执行内容**：调用离线抽取（30 天窗口）→ 模型判定 → 程序校验 → 写入待跟进清单与日子清单。
5. **开关**：只有在记忆模块对该用户不是 `off` 时才会排任务；名单为空 = 完全不排，线上行为不变。

成本量级：每个"有消息的用户"每天 1–3 次调用，输入是最近原话（轻用户整段、重用户按事实型截最近 60 条）。

## 13. 回归轮的上下文裁剪与清单排除（v1 已实现）

已核实现状：带进模型的历史消息按对话模式给，**大多数场景最近 16 条**（少数 8 条或 6 条），
所以清单里的那件事很可能已经在这几行里出现过——必须先排除，否则就是重复。

规则（全部确定性，纯函数，可单测）：

| 间隔          | 保留多少上一段      | 是否给清单             |
| ------------- | ------------------- | ---------------------- |
| 6 小时以内    | 照模式默认（16 条） | 不给                   |
| 6–36 小时     | 照模式默认（16 条） | 给（去掉尾巴里已有的） |
| 36 小时–14 天 | 只留收尾 6 条       | 给                     |
| 14–30 天      | 只留收尾 3 条       | 给                     |
| 30 天以上     | 只留收尾 2 条       | 给                     |

清单排除三层，全部确定性、不靠相似度：
① 原话 id 就在这轮历史里；② 同一件事的原话已经出现在历史文本里；③ 最近 3 天刚问过。
剩下的按"有临近时间的优先、其余按最近更新"排序，最多给 5 条未了结 + 2 条日子。

渲染成几行家常话，只给事实（原话、什么时候说的、什么状态、问过没有），
**不排名次、不建议问哪条**，并写明"不提也是常态"。

尾巴越短，现场内容对模型的拉扯越小，清单被用上的机会才越大——这与前面实测
"现场内容的力量远大于清单"是同一个结论。

## 14. 提问记账（回复生成后写回，v1 已实现）

回复生成后判定"这一轮提到了清单里的哪一条"，写回"上次提起时间 +1"。判定是确定性的：

- 把回复和条目原话都去掉虚词，只看实词；
- 共有实词片段 ≥4 字 → 直接命中；
- 共有片段 ≥2 字且二字实词组合命中率 ≥0.5 → 命中；
- **一轮最多记一条**（分数最高的那条）；都不像就不记。

三条保护：

1. **阈值偏高，宁可少记**：把无关的话错记成"已经问过"，后果是以后该问的永远不问；漏记的后果只是下次再问一次；
2. **同一轮幂等**：同一条 10 分钟内重复调用只算一次，重试不会把"问过"多加；
3. **失败不影响回复**：只记日志，并把判定结果写进对话轨迹（哪条、什么类别、分数多少）便于复盘。

为什么不用"让模型自己申报提了哪条"：那会改回复的输出契约、多一次模型依赖；
文本匹配虽然没有额外成本也不改契约，代价是"完全换词式"的提及会漏记——按上面的取舍，这个漏记可以接受。

至此闭环完整：**清单可选（模型自己挑）→ 提了记账（回复后写回）→ 用户答了由离线任务了结 → 3 天冷却内不再提。**

### 为什么"开启后已发生的回归轮"也全是空清单（2026-09-14 10:40）

按正确口径重查（找"上一条消息在 6 小时以上之前、且这次发言在开启之后"的轮次）：
**开启后近 3 小时已发生回归轮 34 次，其中"发言那一刻已有条目"的 0 次。**

原因是结构性时序，不是检索口径问题：

> 用户在回归轮说话 → 30 分钟后才抽取条目 → **同一轮抽出来的条目只能用在下一轮**。

所以任何用户的第一次回归轮材料必为空；第一条"带条目的回归轮"最早出现在"第一次回归 + 6 小时"之后。

对策：**预热清单**。2026-09-14 10:40 对最近 24 小时活跃、消息数 ≥3 的 800 个用户排了一次性抽取任务
（新建 725 条，其余 75 条当天已有），这样他们下一次隔 6 小时回来时，材料里就会带上真实条目。
