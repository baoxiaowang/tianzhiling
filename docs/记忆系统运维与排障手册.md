## 一、系统架构速查

### 三层存储

| 层 | 载体 | 内容 |
|---|---|---|
| 结构化事实 | Mongo `agent_profile_fact`（主）/ `agent_memory_fact`（遗留） | 规则+LLM 抽取的稳定事实、`profile_source.*` 手工资料、`visual.appearance.*` 外形候选 |
| 人物/时间记忆 | Mongo `user_identity_profile`、`user_known_person`、`user_relative_profile`、`user_relative_fact`、`person_temporal_assertion/profile` | 用户身份、亲属人物、亲属事实、出生/离世等时间断言 |
| 语义索引 | Milvus `conversation_message_memory_v2`（dense HNSW + BM25 sparse，`userId` 分区） | 原始对话 `raw_episode` + 人物语义单元 `person_semantic` |
| 任务/熔断 | Mongo `memory_pipeline_task` + BullMQ `memory-pipeline` + Redis 共享熔断 | 幂等任务、重试、对账 |

### 写入链

`beforeReply` → 入队 `semantic_index`（原始消息）→ `structured_memory`（`enrichUserMessageForReply`：profile facts、人物记忆、时间断言、情绪、关系悬念）→ 需要时再入队 `person_semantic_index`。

### 读取链

- (a) 活跃结构化事实经 `evidence_atom_v1` 直接注入提示词
- (b) Milvus 长期召回经主模型工具 `lookup_chat_evidence`（`relationship_memory` 等来源）

### 离世时长预计算

- AgentEntity 字段：`departureDuration` / `nodeReminder` / `departureDurationComputedAt`
- 调度：每日凌晨 3 点增量（最近 7 天活跃用户）+ 每月 1 号全量 + deathDate 变更即时触发
- 队列：`departure-duration`（BullMQ，前缀 `{tzl-bullmq}`）
- 消费者：**独立 worker 脚本** `apps/node/scripts/departure-duration-worker.js`（**不是** MidwayJS @RuntimeProcessor，原因见第二节）

## 二、已知坑（必须先读，否则必踩）

### 坑 1：MidwayJS `addJobToQueue` 的 repeat 会相互覆盖

**现象**：用 `durationQueue.addJobToQueue(data, { repeat: { pattern, jobId } })` 注册 daily 和 monthly 两个 repeat，结果只有一个生效（后注册的覆盖先注册的，或反过来）。

**根因**：MidwayJS `addJobToQueue` 内部调用 `this.upsertJobScheduler(this.name, repeat, ...)`，**用队列名（`this.name`）作为 jobSchedulerId**，完全忽略 `repeat.jobId`。daily 和 monthly 的 jobSchedulerId 都是 `'departure-duration'` → 幂等覆盖 → 只剩一个。

**源码位置**：`node_modules/@midwayjs/bullmq/dist/framework.js:24-27`

**正确做法**：用原生 BullMQ `Queue.upsertJobScheduler(schedulerId, repeatOpts, jobTemplate)`，schedulerId 各不相同：

```js
const q = new Queue('departure-duration', { connection, prefix: '{tzl-bullmq}' });
await q.upsertJobScheduler('departure-duration-daily', { pattern: '0 3 * * *' }, {
  name: 'departure-duration', data: { type: 'daily' },
  opts: { removeOnComplete: true, removeOnFail: 30 },
});
await q.upsertJobScheduler('departure-duration-monthly', { pattern: '0 3 1 * *' }, {
  name: 'departure-duration', data: { type: 'monthly' },
  opts: { removeOnComplete: true, removeOnFail: 30 },
});
```

### 坑 2：@RuntimeProcessor 和 createWorker 的 worker 处理完 job 不释放

**现象**：job 被处理（计算逻辑执行、数据落库），但 job 状态永远停在 `active`，lock 不释放，completed 列表为空。下次重启会重新入队 startup job，旧 job 永久卡 active。

**根因**：MidwayJS `@RuntimeProcessor` 装饰器创建的 worker，以及 `bullmqFramework.createWorker()` 创建的 worker，处理函数返回后**没有正确调用 `moveToCompleted`**（框架封装缺陷）。标准 BullMQ `new Worker()` 无此问题。

**影响范围**：`departure-duration` 队列（已确认）。`memory-pipeline` 队列用 @RuntimeProcessor 但似乎正常（可能因为 processor 实现不同，或 reconcile job 有其他机制）——**新增队列时务必先验证 job 能否正常 completed**。

**正确做法**：`departure-duration` 队列**移出** `MEMORY_WORKER_QUEUES` 白名单（`apps/node/src/processor/runtime-processor.ts`），用独立 worker 脚本 `apps/node/scripts/departure-duration-worker.js` 消费（标准 BullMQ Worker，正常 markCompleted）。

### 坑 3：独立 worker 必须指定队列前缀

**现象**：独立 worker 启动成功（`worker ready`），但永远收不到 job。

**根因**：BullMQ Worker 默认前缀 `bull:`，而应用队列前缀是 `{tzl-bullmq}`（`config.default.ts:800`，`NODE_BULLMQ_PREFIX` 环境变量）。前缀不匹配 → worker 监听的是另一个队列。

**正确做法**：

```js
const worker = new Worker('departure-duration', handler, {
  connection, prefix: '{tzl-bullmq}', concurrency: 1,
});
```

### 坑 4：生产 git pull 常被本地修改阻塞

**现象**：`git pull origin 20260907` 报 `Aborting` / `Please move or remove them before you can merge`，构建用的是旧代码。

**常见阻塞文件**：
- `apps/admin-node/Dockerfile`（阿里云镜像加速，历史遗留未提交）
- `apps/gateway/ssl/**/*.key` / `*.crt`（生产实际证书，比仓库新）
- `apps/node/scripts/backfill-departure-duration.js`（未跟踪，与远程提交同名时阻塞）

**正确做法**：
```bash
git stash push -m 'temp' -- apps/admin-node/Dockerfile apps/gateway/ssl
# 注意：旧版 git 不支持 `git stash push`，用 `git stash save 'temp'`
git pull origin 20260907
git stash pop
```
如果有未跟踪文件与远程提交同名，先 `mv` 备份再 pull。

### 坑 5：构建后必须验证镜像内容，不能假设构建用了新代码

**现象**：`git pull` 报 Aborting 但输出里有 `Updating fe10759..89ba8fa`，误以为 pull 成功；构建后镜像里仍是旧代码。

**验证方法**（构建后、部署前必做）：
```bash
docker run --rm --entrypoint sh tianzhiling-tzl_node:latest -c '
  grep -c "关键字" /workspace/apps/node/dist/configuration.js
  grep -c "关键字" /workspace/apps/node/scripts/xxx.js
'
```
确认新代码在镜像里再 `docker compose up -d --force-recreate`。

### 坑 6：job 卡 active 时的清理方法

当 job 因框架缺陷卡 active（lock 不释放），手动清理：
```bash
# 清 lock
docker exec tzl_redis redis-cli -n 0 del '{tzl-bullmq}:<queue>:<jobId>:lock'
# 从 active 列表移除
docker exec tzl_redis redis-cli -n 0 lrem '{tzl-bullmq}:<queue>:active' 1 '<jobId>'
# 删 job hash
docker exec tzl_redis redis-cli -n 0 del '{tzl-bullmq}:<queue>:<jobId>'
```

## 四、排障流程（按顺序）

1. **看日志**：`docker logs tzl_memory_worker` / `docker logs tzl_node`，先看有没有 error/warn，再看关键流程日志
2. **查队列**：getJobCounts（active/waiting/completed/failed/delayed），看 job 卡在哪
3. **查 Redis**：`--scan --pattern` 看 repeat key、lock key、job hash
4. **查 Mongo**：数据是否落库、计算时间戳
5. **容器内最小验证**：`docker exec tzl_memory_worker node -e "..."` 直接跑逻辑，不重新构建
6. **验证镜像**：`docker run --rm --entrypoint sh` grep 确认代码版本
7. **读源码**：框架行为异常时，直接读 `node_modules/@midwayjs/bullmq/dist/` 和 `node_modules/bullmq/dist/`

## 六、通用工作原则（本次任务总结）

1. **涉及框架封装行为，先读源码再动手**——MidwayJS/BullMQ 的封装行为不读源码猜不到
2. **逻辑变更先在容器内 `node -e` 最小验证**，确认后再构建部署（构建一次 5-40 分钟，试错成本高）
3. **问题定位先查数据（Redis/Mongo/日志），不靠猜**
4. **构建部署前验证镜像内容**，不能假设构建用了新代码
5. **生产 git pull 前先检查本地修改**，有则 stash
